# Upgrading Strictly Laravel

Strictly Laravel is two packages released together under one version: `mrsafalpiya/strictly-laravel` (Composer) and `@mrsafalpiya/strictly-laravel` (npm). An existing app picks up a release like this.

## Every update

1. **Update both packages to the same version.** `composer update mrsafalpiya/strictly-laravel` and `pnpm update @mrsafalpiya/strictly-laravel` (or your package manager's equivalent). While their versions differ, the Vite plugin prints a `[strictly]` warning in `composer dev` and in every build.
2. **Run `php artisan strictly:install` again.** It applies every hook a release added since you installed, restores any hook the app lost, and converts any Base Kit file a newer release knows how to convert, if that file still holds its upstream content. Anything else it leaves alone: files Kit Conversion already converted (by any release), Base Kit files you edited, and your `config/strictly.php`. It prints one row per hook and per Base Kit file. A hook it can't apply reads `not applied`, followed by what to do by hand; nothing is forced.
3. **Make the changes listed under [Releases](#releases)** for every release after the one you're upgrading from, up to and including the one you're upgrading to.
4. **Run `composer ci:check`.** Its first step, `ci:check:install`, runs `php artisan strictly:install --check`. That command changes nothing. It fails, and names each hook, while the installer would still change something or can't apply a hook, so you can't miss step 2, or a change from step 3 that has a check.

Running `strictly:install` on an app that is fully up to date changes nothing: every row reads `unchanged`.

### Config keys

`config/strictly.php` is yours: the installer publishes it once and never edits it again. The package merges its own defaults under yours (`mergeConfigFrom`), so your app gets any top-level key a release adds with its default value, without a change to your file. A release that needs a value from you lists it below, with a check.

## Releases

Newest first. Each entry lists the app-side changes the release needs. Each change says how to apply it and which check fails until it is applied.

### Unreleased

- **Model keys are branded by their model and field, and every key property declares its model (Problem P-128, ADR-0009).** A Data property that holds a model's key is now generated as `Key<'User', 'id', number>`, not `number`: the primary key of every Data class built from a model (`fromModel(User $user)`), each field its routes bind it by, and any property declaring `#[KeyOf(User::class)]` (`StrictlyLaravel\Data\KeyOf`; `#[KeyOf(Issue::class, 'number')]` for another field), now in input and query classes too. Route functions take the key of the field their route binds by: `Key<'Issue', 'number', number>` for `{issue}` bound by `number`. `RouteKey<'Issue', number>` and `#[RouteKeyOf]` keep working and name the key of the model's route key name. To upgrade: add `#[KeyOf(Model::class)]` to every property PHPStan lists (a value that is no model's key, such as another service's id, takes `@phpstan-ignore strictly.keyOf (the reason)`); then fill those fields from the keys the server sent (`member.id`), and turn a select's value back into a key by looking it up among its options' keys instead of `Number(value)`. Type state that holds keys by the input (`useState<BulkUpdateIssuesData['ids']>([])`), not `number[]`. A feature test that renders a key of a row that doesn't exist (an activity payload with a made-up comment id) now fails: create the row (P-116). **Check:** `ci:check:test` fails with `strictly.keyOf` (`App\Data\StoreIssueData::$assigneeId is named like a model's key but declares no model, …`) on every property that needs `#[KeyOf]`, listing them all; once they declare it, `ci:check:tsc` fails with TS2322 or TS2345 (`Type 'number' is not assignable to type 'number & { readonly [keyOf]: "User.id"; }'.`) wherever a plain number, or another model's or field's key, fills one.
- **Translation calls in PHP are checked (Problem P-137).** The PHPStan rule behind `strictly.translationKey`, `strictly.translationParams`, `strictly.translationPlural` and `strictly.translationDynamic` checks `__()`, `trans()`, `trans_choice()`, `Lang::get()`, `Lang::choice()` and the Translator's `get()` and `choice()` as `tsc` checks `t()` and `choice()`: a `group.item` key must be defined in the default locale's lang files (or be one of Laravel's own, such as `validation.required`), the replacements must be exactly the message's `:params` (`trans_choice()` may leave out `count`), and a pluralised message must go through `trans_choice()`, any other through `__()`. Fix each key or param it reports. A key built at runtime is reported too: make it a literal or a union of literals (`__($archived ? 'projects.flash.archived' : 'projects.flash.restored')`), or suppress it with `@phpstan-ignore strictly.translationDynamic (why every key it builds exists)`. Text that no lang file defines (`__('Profile updated.')`) still renders as it is and passes (P-163). **Check:** `ci:check:test` fails with `Translation key '…' isn't defined in locale en.` and the rule's other messages at each such call.
- **A pluralised message renders with `choice()`, not `t()` (Problem P-136).** `@/generated/translations` now also exports `choice(key, count, params?)`, which picks a `|` message's form for the count as `trans_choice()` does and fills `:count`. `t()` rejects the key of any message that contains `|` (`'apple|apples'`, `'{0} None|[1,*] :count'`), which it used to render whole, and `choice()` rejects every other key. Render each such message with `choice()`; a message that holds a literal `|` and isn't pluralised must move the `|` out of the message (P-161). The locale parity test now also fails when a locale's message is pluralised where the default locale's isn't, or the other way round: give every locale's message `|` forms, or none, as the default locale's has. **Check:** `ci:check:tsc` fails with TS2345 (`… is not assignable to parameter of type '"issues.count is a plural message: use choice()"'.`) at each `t()` of a pluralised message, and `ci:check:test` fails with `de: issues.count isn't plural, but the en message is, …` for each mismatched locale.
- **An input's `authorize()` and `rules()` receive the route's bound models (Problem P-126).** A parameter typed as a model now gets the model the route binds to the parameter of the same name (`authorize(Comment $comment)` for `{comment}`), where it used to get a new, empty model. Replace each `$request->route('comment')` read and its `instanceof` check in an input with such a parameter. An input whose model parameter is named differently from the route's, or whose route leaves it unbound (the action doesn't take the model), now fails its request with a `LogicException` naming the parameter and the route instead of checking an empty model: rename the parameter, or take the model in the action. Validating such an input outside a request (`validate()` from a command or a unit test) throws too (P-155). A model parameter of `authorize()` or `rules()` on a query class or a plain Data class, which still gets an empty model, is rejected. **Check:** `ci:check:test` fails: the request's feature test (Contract Coverage requires one for every form endpoint) on a mismatched parameter, and PHPStan (`strictly.routeModelParameter`) on a model parameter outside an input class.
- **A route whose action takes no query class takes no query string, and controllers read the query string only through a query class (Problem P-106).** The route functions of a controller action without a query class, of a closure route and of a vendor action `config/strictly.php` declares no query class for now type `query` and `mergeQuery` as `NoQueryClass`, which no value fits, and the PHPStan rule `strictly.queryRead` rejects `$request->query(…)`, `$request->query->…`, `request()->query(…)` and `Request::query(…)` in a controller. Give each action whose links send a query string, or that reads one, a query class (a final Data class extending `StrictlyLaravel\Data\QueryData`, skill `strictly-add-query-filters`), read the keys from it, and move a closure route that takes one into a controller action. Links that follow a paginator's own URLs (`<Pagination>`, `<InfiniteScroll>`) need no change. **Check:** `ci:check:tsc` fails with TS2353 (`'tab' does not exist in type 'NoQueryClass'`) on each link that sends a query string to such a route, and `ci:check:test` fails on each read from the request (`strictly.queryRead`).
- **Broadcast notifications and model broadcasts are read through an app event (Problem P-142).** `strictly/typed-broadcasts` now also rejects Echo's `useEchoNotification()` and `useEchoModel()`, whose payloads (a notification's `toBroadcast()`, a `BroadcastsEvents` model) have no generated type. Where the app reads one, broadcast an event of its own with a `BroadcastsData` payload alongside the notification or model change, and listen for it with `useChannelEvent()` from `@/generated/broadcasting`. **Check:** `ci:check:lint` fails on each `useEchoNotification()` and `useEchoModel()` call.
- **Public broadcast channels are declared in `config/strictly.php` (Problem P-143).** `publicChannel()` from `@/generated/broadcasting` now takes only a public channel the new `public_channels` key declares, by its pattern and with its parameters (`publicChannel('projects.{project}.public', { project })`), and each broadcast Contract checks every channel the event was broadcast on, public ones included. Add the key to your `config/strictly.php` (the installer never edits it; copy it from `vendor/mrsafalpiya/strictly-laravel/stubs/strictly.php`) and list each public channel the app broadcasts on or listens to: `'status'`, or `'projects.{project}.public' => ['project' => Project::class]` to type a parameter as the model's route key. A public channel defined in `routes/channels.php` as a private one only so that `channel()` could name it can move back to `new Channel(…)` and `publicChannel()`. **Check:** `ci:check:tsc` fails on each `publicChannel()` of an undeclared channel (`… is not assignable to parameter of type 'never'.` while none is declared), and on each recorded broadcast on one (`… is not assignable to type 'BroadcastChannelName'.`); `ci:check:generate` fails on a declaration that names no channel.
- **A broadcast event declares the channels it is sent on, and listeners take only its events (Problem P-144).** Add `#[BroadcastsOn('issues.{issue}')]` (`StrictlyLaravel\Broadcasting\BroadcastsOn`) to every event that implements `ShouldBroadcast`, once for each channel pattern its `broadcastOn()` sends it to, as `routes/channels.php` defines it or `public_channels` in `config/strictly.php` declares it. `useChannelEvent()` then takes an event only on a channel whose pattern it declares, each broadcast Contract checks the channels `broadcastOn()` really used against the declaration, and Contract Coverage needs a feature test that broadcasts the event on each declared channel. A public channel in `public_channels` that no event declares is a coverage gap too: remove it, or declare it on the events sent there. **Check:** `ci:check:test` fails on each event without one (`strictly.broadcastsOn`), `ci:check:generate` on a pattern the app doesn't know, `ci:check:tsc` on each listener for an event on a channel it isn't declared for and on each recorded broadcast to an undeclared one, and `ci:check:coverage` on each declared channel no test broadcasts the event on.
- **A Data class with `rules()` nested in an input extends `InputData` too (Problem P-099).** laravel-data merges a class's `rules()` with the rules inferred from its types only when that class carries `#[MergeValidationRules]`, which `InputData` provides, and it reads that from each nested class separately. So a plain Data class with `rules()` used as a property of an input or query class, or as an item of a list, map or `DataCollection` there, at any depth, had its inferred rules (`required|string` and the like) dropped. Make each such class extend `StrictlyLaravel\Data\InputData` instead of `Data`; nothing else changes for it. **Check:** `ci:check:test` fails with `strictly.inputData` (`…::$task nests App\Data\TaskData, whose rules() replace the rules inferred from its types because it doesn't extend StrictlyLaravel\Data\InputData.`) on each property that nests one.
- **AI coding agents get the Strictly Laravel guidance through Laravel Boost (Problem P-146).** The Composer package now requires `laravel/boost`, so `composer update` installs it, and ships a Boost core guideline and one skill per workflow. `strictly:install` adds `@php artisan boost:update --ansi` to `composer.json`'s `post-update-cmd`, so every `composer update` refreshes the agent files Boost generates from them. Run `php artisan boost:install` once in each clone and pick your agents; the Strictly Laravel guidance is preselected. The files it writes (`CLAUDE.md`, `AGENTS.md`, `.claude/`, `.mcp.json`, `boost.json`, …) are gitignored by the Base Kit; if your `.gitignore` lost those entries, add them back, or the copied guidance gets committed and goes stale. ## The release-check convention (for Overlay maintainers)

Every release that needs a change in existing apps adds an entry under [Releases](#releases) before it is tagged. Each change in the entry names the Problem it serves and how to apply it, and it gets a **release check**: something in `ci:check` that fails until the change is applied. Use the first of these that fits:

1. **The installer can make the change.** Make it a hook in `StrictlyLaravel\Console\InstallCommand::hooks()`. The entry then just says "applied by `strictly:install`". No other check is needed, because `ci:check:install` fails on any hook that hasn't been applied.
2. **Only the app's developer can make the change, but the installer can tell whether it's made.** Make it a hook that changes nothing. When the change isn't there, the hook throws an exception that says what to do and links its entry here (`see vendor/mrsafalpiya/strictly-laravel/UPGRADE.md#<version>`). The installer reports that hook as `not applied`, so `ci:check:install` fails until the developer makes the change. This is how a vite.config.ts the installer can't patch is handled today (scenario `vite-plugin-unpatchable-fails-install-check`).
3. **The change is in app code.** Make the check a rule in the earliest tool that can express it (PHPStan, then oxlint, then `tsc`, then a test), with a message that links the entry.
4. **Nothing can check it.** Say so in the entry ("No check: …") and say why.

A change to a file under `kit/` reaches only apps whose copy of that file still holds its upstream content. An app that already holds an earlier conversion keeps it (its hash is in `earlierConversions`, ADR-0005). If the new conversion matters to existing apps, list it under the release as a change to make by hand, with a release check from the list above.

Each release check is proven like any other change: a harness scenario where the change is missing fails with the check's message, and one where it is applied passes (see `docs/agents/developing-the-overlay.md`).
