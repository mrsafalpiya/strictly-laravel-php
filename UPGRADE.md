# Upgrading Strictly Laravel

Strictly Laravel is two packages released together under one version: `mrsafalpiya/strictly-laravel` (Composer) and `@mrsafalpiya/strictly-laravel` (npm). An existing app picks up a release like this.

## Every update

1. **Update both packages to the same version.** `composer update mrsafalpiya/strictly-laravel` and `pnpm update @mrsafalpiya/strictly-laravel` (or your package manager's equivalent). While their versions differ, the Vite plugin prints a `[strictly]` warning in `composer dev` and in every build.
2. **Run `php artisan strictly:install` again.** It applies every hook a release added since you installed, restores any hook the app lost, and converts any Base Kit file a newer release knows how to convert, if that file still holds its upstream content. Anything else it leaves alone: files Kit Conversion already converted (by any release), Base Kit files you edited, and your `config/strictly.php`. It prints one row per hook and per Base Kit file. A hook it can't apply reads `not applied`, followed by what to do by hand; nothing is forced.
3. **Make the changes listed under [Releases](#releases)** for every release after the one you're upgrading from, up to and including the one you're upgrading to.
4. **Run `composer ci:check`.** Its first step, `ci:check:install`, runs `php artisan strictly:install --check`. That command changes nothing. It fails, and names each hook, while the installer would still change something or can't apply a hook, so you can't miss step 2, or a change from step 3 that has a check.

Running `strictly:install` on an app that is fully up to date changes nothing: every row reads `unchanged`.

### Config keys

`config/strictly.php` is yours: the installer publishes it once and never edits it again. The package merges its own defaults under yours (`mergeConfigFrom`), so your app gets any top-level key a release adds with its default value, without a change to your file. A release that needs a value from you lists it below, with a check.

### Unreleased

- **AI coding agents get the Strictly Laravel guidance through Laravel Boost (Problem P-146).** The Composer package now requires `laravel/boost`, so `composer update` installs it, and ships a Boost core guideline and one skill per workflow. `strictly:install` adds `@php artisan boost:update --ansi` to `composer.json`'s `post-update-cmd`, so every `composer update` refreshes the agent files Boost generates from them. Run `php artisan boost:install` once in each clone and pick your agents; the Strictly Laravel guidance is preselected. The files it writes (`CLAUDE.md`, `AGENTS.md`, `.claude/`, `.mcp.json`, `boost.json`, …) are gitignored by the Base Kit; if your `.gitignore` lost those entries, add them back, or the copied guidance gets committed and goes stale. Until a clone has run `boost:install`, `composer update` ends with Boost's "Please set up Boost with [php artisan boost:install] first." Applied by `strictly:install`. **Check:** `ci:check:install` reads `Composer scripts: boost:update after composer update (missing)` until then.
- **Broadcast payloads are Data classes, and broadcasts are typed end to end (Problems P-052, P-053, P-054).** Every event that implements `ShouldBroadcast` must use `StrictlyLaravel\Broadcasting\BroadcastsData` and return its payload from `broadcastData()`, declaring its Data class as the return type (`public function broadcastData(): CommentData`), instead of public properties or its own `broadcastWith()`. Listen with `useChannelEvent(channel('issues.{issue}', { issue }), 'CommentPosted', cb)` from `@/generated/broadcasting` instead of Echo's `useEcho()`, `useEchoPresence()` or `useEchoPublic()`; the new oxlint rule `strictly/typed-broadcasts`, which `strictly:install` adds to the Vite+ lint config, rejects those. Every event a feature test broadcasts is recorded as a Contract, so each event needs a feature test that broadcasts it, with every shape its payload permits. **Check:** `ci:check:install` fails until the installer re-runs; then `ci:check:test` fails on each event without a Data class payload (`strictly.broadcastData`), `ci:check:lint` on each `useEcho()`, and `ci:check:coverage` on each event no test broadcasts.
- **Translations are typed, and every locale must match the default one (Problems P-055, P-056, P-057).** `strictly:generate` now also writes `@/generated/translations`, whose `t(key, params)` takes only the keys of the default locale's lang files (`app.locale`) and exactly the `:params` of each message. `strictly:install` publishes `tests/Feature/LocaleParityTest.php`, which fails while another locale lacks a key or a param of the default locale's, or has one it doesn't: an app with partially translated locales sees each gap listed and must complete or remove it. Applied by `strictly:install`. **Check:** `ci:check:install` reads `tests/Feature/LocaleParityTest.php (missing)` until then. A lang file that doesn't return an array, or a `lang/<locale>.json` that isn't an object, now fails `ci:check:generate`.
- **`import.meta.env` is typed from `.env.example` (Problem P-058).** `@/generated` turns on Vite's `strictImportMetaEnv` and declares each `VITE_*` variable `.env.example` lists as a string, so reading one it doesn't list fails `tsc`. Add every `VITE_*` variable the app reads to `.env.example`. **Check:** `ci:check:tsc` fails with TS2339 (`Property 'VITE_…' does not exist on type 'ImportMetaEnv'`) where an unlisted variable is read.
- **A build fails when its environment lacks a `VITE_*` variable `.env.example` lists (Problem P-140).** Set each one in the `.env` (or environment) of every place that runs `vite build`, CI and deployments included; an empty value counts. The dev server only warns. **Check:** the build itself fails with `[strictly] .env.example lists VITE_…`; `ci:check` doesn't build, so no `ci:check` step fails.
- **`usePage()` takes no hand-written type argument (Problem P-059).** The new oxlint rule `strictly/typed-page-props` rejects `usePage<T>()` unless `T` is a generated `PageProps<'component'>`; move a setting or feature flag such a type described into the shared props Data class. Applied by `strictly:install`, which adds the rule to the Vite+ lint config. **Check:** `ci:check:install` fails until the installer re-runs, then `ci:check:lint` fails on each hand-typed `usePage<T>()`.
- **Route parameters bound to a model take that model's route key (Problem P-003).** A route whose action type-hints `Passkey $passkey` now takes `RouteKey<'Passkey', number>`, not any number, so code that passes a plain `number` fails `tsc`. Pass the Data object or its key instead, and type ids you hand around by their Data class (`PasskeyData['id']`). An app whose `resources/js/components/manage-passkeys.tsx` and `passkey-item.tsx` hold an earlier Kit Conversion types `handleDelete`'s and `onDelete`'s `id` as `number`: change both to `PasskeyData['id']` (imported from `@/generated`), as the current conversion does. **Check:** `ci:check:tsc` fails with TS2345 at `visit(destroy(id), …)` until then.
- **A route parameter that names a binding field needs its model type-hinted (Problem P-002).** `strictly:generate` fails on a route such as `{workspace:slug}` whose action takes `string $workspace`, and lists each one. Type-hint the model (`Workspace $workspace`). **Check:** `ci:check:generate`.
- **Vendor routes are typed by the declarations in `config/strictly.php` (Problems P-025, P-050, P-100).** A new install's `config/strictly.php` declares the payloads, query string and two-factor JSON responses of the Base Kit's Fortify actions; an existing app's file declares none, since the installer never edits it. Copy the `vendor_inputs`, `vendor_queries` and `vendor_responses` keys from `vendor/mrsafalpiya/strictly-laravel/stubs/strictly.php`, copy the classes they name that the app lacks from `vendor/mrsafalpiya/strictly-laravel/kit/app/Data/Auth/` (`EnableTwoFactorData`, `ResetPasswordQueryData`, `TwoFactorSecretKeyData`), add `remember` to `App\Data\Auth\RegisterData` as the kit's has it, and drop the type argument of every `<TypedForm<…>>` (an earlier Kit Conversion wrote one in each Fortify form). Contract Coverage then lists the Fortify actions no feature test submits to or calls; the kit's `tests/Feature/ContractCoverageTest.php` has tests for them. **Check:** `ci:check:lint` fails on each `<TypedForm<…>>` (`strictly/typed-forms`), and once they are dropped `ci:check:tsc` fails on every `field()` of a Fortify form until its payload is declared.
- **Feature tests check what vendor FormRequests and GETs with a query class read (Problem P-025).** A key read through a FormRequest the action takes (`$request->input('x')` on Fortify's `LoginRequest`), or by a GET action that takes a query class, must be a field of the declared or type-hinted class. **Check:** the request's Contract fails `ci:check:tsc` until the key is declared or no longer read.
- **Feature tests check route keys and give every table its own id range (Problem P-116).** A test that asserted a literal id (`1`) for a fresh row on SQLite now sees ids such as `4000001`: assert the model's own `id` instead. **Check:** the test fails.

## The release-check convention (for Overlay maintainers)

Every release that needs a change in existing apps adds an entry under [Releases](#releases) before it is tagged. Each change in the entry names the Problem it serves and how to apply it, and it gets a **release check**: something in `ci:check` that fails until the change is applied. Use the first of these that fits:

1. **The installer can make the change.** Make it a hook in `StrictlyLaravel\Console\InstallCommand::hooks()`. The entry then just says "applied by `strictly:install`". No other check is needed, because `ci:check:install` fails on any hook that hasn't been applied.
2. **Only the app's developer can make the change, but the installer can tell whether it's made.** Make it a hook that changes nothing. When the change isn't there, the hook throws an exception that says what to do and links its entry here (`see vendor/mrsafalpiya/strictly-laravel/UPGRADE.md#<version>`). The installer reports that hook as `not applied`, so `ci:check:install` fails until the developer makes the change. This is how a vite.config.ts the installer can't patch is handled today (scenario `vite-plugin-unpatchable-fails-install-check`).
3. **The change is in app code.** Make the check a rule in the earliest tool that can express it (PHPStan, then oxlint, then `tsc`, then a test), with a message that links the entry.
4. **Nothing can check it.** Say so in the entry ("No check: …") and say why.

A change to a file under `kit/` reaches only apps whose copy of that file still holds its upstream content. An app that already holds an earlier conversion keeps it (its hash is in `earlierConversions`, ADR-0005). If the new conversion matters to existing apps, list it under the release as a change to make by hand, with a release check from the list above.

Each release check is proven like any other change: a harness scenario where the change is missing fails with the check's message, and one where it is applied passes (see `docs/agents/developing-the-overlay.md`).
